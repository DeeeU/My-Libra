# データ同期アーキテクチャ

## 設計方針: オフラインファースト

SwiftData がローカルキャッシュ兼オフラインストアとして機能。
SyncService がバックグラウンドで Supabase との同期を管理。

## 同期フィールド (SwiftData モデル追加分)

```swift
var userId: String?           // Supabase user ID (nil = ローカルのみ)
var syncStatus: SyncStatus    // .local / .synced / .pendingUpload / .pendingDelete
var localUpdatedAt: Date      // ローカル更新時刻
var remoteUpdatedAt: Date?    // サーバー更新時刻
```

Item には追加で:
```swift
var imageUrl: String?         // Supabase Storage のパス
```

## SyncStatus フロー

```
[新規作成] ──→ .local
                 │
                 ▼ (ログイン + 初回同期)
            .pendingUpload
                 │
                 ▼ (push 成功)
              .synced
                 │
                 ├── ローカル変更 ──→ .pendingUpload ──→ .synced
                 └── 削除要求 ──→ .pendingDelete ──→ (サーバー削除後ローカル削除)
```

## Push 同期 (ローカル → リモート)

1. `syncStatus == .pendingUpload` のレコードを `FetchDescriptor` で取得
2. Supabase REST API で `upsert` (INSERT or UPDATE)
3. 成功後 `syncStatus = .synced`, `remoteUpdatedAt = Date()`

## Pull 同期 (リモート → ローカル)

1. `updated_at > lastSyncDate` でサーバーから差分取得
2. ローカルに同じ ID があれば:
   - `syncStatus != .pendingUpload` の場合のみ上書き (Last-write-wins)
   - `.pendingUpload` の場合はスキップ (ローカル変更を優先)
3. ローカルに存在しなければ新規 INSERT

## 競合解決: Last-Write-Wins (V1)

- シンプルな実装として、タイムスタンプベースの競合解決を採用
- `pendingUpload` 状態のローカル変更はサーバー側の更新で上書きされない
- 将来的にはマージ戦略やCRDTの導入を検討

## 既存データ移行

初回ログイン時の処理:
1. `userId == nil` の全レコードを検索
2. 現在のユーザー ID を付与
3. `syncStatus = .pendingUpload` に設定
4. `UserDefaults` に移行完了フラグを保存
5. 次回同期で自動的にサーバーへ push

## コンポーネント構成

```
SyncCoordinator (@Observable)
├── performSync(context:) - フル同期 (push → pull)
├── migrateIfNeeded(userId:, context:) - 初回移行
├── isSyncing: Bool
├── lastSyncDate: Date?
└── syncError: String?

SyncService (@MainActor)
├── pushItems / pushWishlistItems / pushCategories
├── pullItems
└── migrateLocalData

ImageSyncService (actor)
├── uploadImage(data:, itemId:) → path
├── downloadImage(path:) → Data
├── deleteImage(path:)
└── compressImage (500KB以下に圧縮)
```

## 既存 @Query への影響

**変更不要**。SwiftData はローカルキャッシュであり、端末上のデータは全て現在のユーザーのもの。
ユーザー分離は Supabase RLS で実現するため、既存の `@Query` はそのまま動作する。
